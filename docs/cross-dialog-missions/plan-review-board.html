01 · Outcome

Как движется миссия

Нажмите на узел, чтобы увидеть его ответственность и границы.

01

Mission coordinator

Владеет только внешним DAG и общим результатом.

  • Создаёт только ready peer-задачи.
  • Проверяет receipts и передаёт bounded context.
  • Интегрирует commits в topological order.
  • Финализирует единый gate.

02 · Product contract

Зачем и как запускать

Mission полезна там, где ручная координация уже дороже отдельного workflow.

01 / Параллельность

Независимые workstreams

Backend, clients, docs или packages идут одновременно в отдельных worktrees.

02 / Зависимости

Правильный порядок

Consumer не стартует, пока producer не вернул проверенный contract receipt.

03 / Контекст

Одна node — один outcome

Высокоуровневая node может поднять lazy team, сохранив внешнюю границу простой.

04 / Изоляция

Без гонки за checkout

Writer nodes получают worktrees, а локальные writers — непересекающиеся scopes.

05 / Доверие

Receipt вместо «готово»

Claims проверяются по source, commits, artifacts и командам.

06 / Итог

Один verification verdict

После APPROVED exact evidence bundle проходит fenced delivery, затем durable checkpoint фиксирует delivered revision и Done.

Размер S/M/L/XL не выбирает workflow
РазмерТипичное действие
SОбычно direct; mission возможна только при реальной межконтекстной зависимости.
MDirect или team-lazy; mission допустима при двух самостоятельных outcomes.
LTeam-up или mission — выбор определяет topology.
XLСначала декомпозиция, затем один или несколько team-up/mission workflows.

M API + SDK с producer → consumer зависимостью может быть mission. XL тесно связанный рефакторинг может остаться team-up. Размер влияет на стоимость и декомпозицию, но не является authorization.

Выбирать mission

  • Есть минимум два отделимых workstreams.
  • Есть producer → consumer зависимости.
  • Нужна независимость исследовательских контекстов.
  • Нужны worktrees и последовательная интеграция.
  • Нужен implement/test/review/fix граф.
  • Работу потребуется возобновлять.

Не выбирать mission

  • Локальная правка одного файла.
  • Writers неизбежно меняют одни строки.
  • Не решена продуктовая развилка.
  • Нужно только объяснение, ревью или план.
  • Нет peer thread tools, а видимые задачи обязательны.

Простыми словами: mission или team-up?

ОДНА КОМНАТА

$qtim-team-up

Один главный диалог поднимает внутренних специалистов и вместе с ними доводит один связный результат через implement → test → fix → review.

Выбирайте: когда цель одна, контекст общий, а главная сложность — цикл доводки.

НЕСКОЛЬКО КОМНАТ

$qtim-mission

Coordinator управляет несколькими самостоятельными диалогами. У каждого свой outcome, контекст и worktree; результаты передаются по проверенному DAG.

Выбирайте: когда есть разные результаты, worktrees или зависимость A → B.

Mission — не «более мощный team-up». Исправление одной checkout-фичи с тестами — team-up. Миграция API, где SDK ждёт backend-контракт, — mission. Несколько ролей в один проход без циклов — обычный team-lazy.

Три режима активации

явное разрешение

AUTO-START

«Запусти» + Approved source либо multi-peer shape + однозначный Approved DAG + зелёный preflight. Первые ready-задачи создаются без второго checkpoint.

нужен выбор

PREVIEW

Raw goal, Fork Test, dirty base, model или budget ambiguity. До подтверждения ни одного create_thread.

без запуска

RECOMMEND

$qtim-feature или другой workflow показывает выбор, topology и готовую команду, но не создаёт subagents или peer-задачи.

Размер L/XL никогда сам не переводит RECOMMEND в AUTO-START. Нужна явная displayed mission-команда или approval после полного Approved mission preview. Короткое «Запускай предложенное» после одной feature-рекомендации сначала открывает PREVIEW без create_thread.

AUTO-START: обязательные условия
  1. Executable `$qtim-mission` с Approved source/multi-peer shape либо недвусмысленная просьба провести несколько Codex peer tasks как одну mission.
  2. Approved plan/brief с acceptance criteria и без открытых Fork Tests.
  3. Однозначный App project и доступные thread tools.
  4. Понятный base/snapshot, безопасные scopes и worktrees.
  5. Ацикличный DAG и утверждённые budgets.
  6. Для lazy node — явно Approved Sol/Ultra pair; нужные роли можно выполнить сразу или runtime waves.
  7. Не требуется новый model override, destructive action или пользовательское решение.
Когда coordinator обязан остановиться
Approval/permission, новая необратимая развилка, опровергнутый premise, конфликт интеграции, scope violation, потерянный handle, исчерпанный budget или расширение исходного scope. SessionStart только напоминает; resume всегда явный.
03 · System design

Два уровня ownership

Внешний coordinator управляет миссией. Внутренний node lead управляет только локальной lazy-командой.

LEVEL 1

Mission coordinator

  • Peer-задачи и DAG.
  • Dependency context packs.
  • Runtime handles и retries.
  • Commit integration.
  • Final verification verdict.
LEVEL 2

Peer task / node lead

  • execution: direct | lazy.
  • Все materially needed roles, без числовой квоты.
  • Explicit writer/read-only policy; disjoint local write scopes.
  • Проверка role claims.
  • Один агрегированный node receipt.
concurrency:
  policy: demand-driven
  overflow: runtime-waves

execution: lazy

  rolePolicy: minimum-sufficient
  leadProfile:

В scope v1

Acyclic DAG, read-only/writer nodes, App peer tasks, worktrees, demand-driven local lazy teams, runtime waves, context packs, receipts, transactional sequential integration, clean verifier, bounded fixes, single-owner resume/fallback.

Вне scope v1

Daemon/MCP scheduler/SQLite, tmux, mixed Claude teams, recursive missions, node-local team-up, third-level fan-out, cloud/cross-host handoff, automatic approvals, foreign task cleanup, cyclic DAG и concurrent integration.

Scheduler: 11 обязательных шагов
Validate DAG → find ready → start everything accepted by runtime → create worktree → pass explicitly approved lazy lead profile → reconcile threadId → title task → wait in batches ≤8 → surface needs_input → validate receipt before downstream.
Интеграция и final gate
Writer возвращает bounded commit. Coordinator проверяет base/scope, делает cherry-pick в disposable transaction worktree, запускает affected gate и только затем из clean integration worktree делает full-OID ancestry check, atomic exact-old update-ref и exact-final clean-tree verification. Red gate не сдвигает Approved HEAD. Reserved terminalVerifier исключён из обычных scheduler waves; после полного project validation создаётся ровно одна отдельная read-only verification-задача. NOT APPROVED создаёт bounded fix nodes; исчерпанный budget даёт Blocked, а не ложный Done. После APPROVED exact bundle проходит fenced delivery, затем отдельный монотонный checkpoint записывает Done и deliveredEvidenceRevision, равный независимо перечитанному promoted HEAD.
