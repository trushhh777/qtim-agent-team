# qtim Onboard — глубокий онбординг dev-памяти

Setup делает быстрый discovery (5-10 tool calls) — этого хватает для charter, но `memory/` рождается тощей. Onboard — отдельный глубокий проход, чтобы команда не была «слепой» первые эпики.

Когда: сразу после `$qtim-setup` на существующей кодовой базе или позже, когда память ощутимо отстаёт от кода. Для greenfield-проекта не нужен. Продуктовый взгляд (разделы, акторы, глоссарий, метрики) — зона `$qtim-product-onboard`; здесь — инженерный: архитектура, инварианты кода, конвенции.

Invocation of this skill is explicit permission to spawn the read-only researcher subagents described below.

## Шаги

### 1. Инвентаризация

Прочитай `.codex/team-charter.md` (если нет — предложи `$qtim-setup` и остановись) и текущее `memory/` — что уже записано, дубликаты не создавать. Составь список подсистем для исследования: слои из discovery (фронт-модули, серверные routes, схема БД и миграции, realtime, инфра/CI) + крупные каталоги.

### 2. План и подтверждение объёма

Покажи список исследователей (подсистема -> что ищем) и объём (N параллельных агентов). Fan-out жжёт токены — дождись подтверждения пользователя. Очень большой репозиторий — итерациями: ядро сейчас, периферия следующим проходом.

### 3. Fan-out исследователей (read-only)

Параллельно, `explorer` / `worker` на подсистему, с чётким заданием:

- точки входа и карта модуля;
- реальные конвенции (именование, паттерны) с прецедентами `file:line`;
- инварианты, **соблюдаемые кодом** (не желаемые): владение данными, каскады, проверки доступа, переходы состояний;
- известные грабли (TODO/FIXME/workaround-комментарии, подозрительные обходы).

Исследователь возвращает структурированный вывод — в память сам не пишет.

### 4. Синтез (main thread)

Сведи отчёты в файлы `memory/` по layout из charter (`project-map.md`, `invariants.md`, `commands.md`, при необходимости topic-файлы). Конфликт между отчётами — проверь сам по коду. Каждый инвариант — с прецедентом `file:line`; гипотезы помечай как гипотезы.

### 5. Индекс и отчёт

Обнови `memory/MEMORY.md`; пользователю — что записано и что осталось белым пятном (кандидаты на следующий onboard-проход).

## Правила

- Исследователи read-only: код не правят, в память не пишут — пишет только main thread (контроль дублей и качества).
- Не дублировать `AGENTS.md`/README — память дополняет их, не пересказывает.
- Инвариант без подтверждения в коде инвариантом не записывается.
- Объём: файлы памяти — сжатые факты, не эссе; глубокие детали — отдельными topic-файлами со ссылкой из `MEMORY.md`.
- Повторный запуск обновляет существующие файлы памяти, а не создаёт дубли.
