# qtim Debug Loop

> Дисциплина qtim; Codex-адаптация `diagnosing-bugs` из [mattpocock/skills](https://github.com/mattpocock/skills), MIT.

Диагностируй нетривиальные баги через воспроизводимый сигнал, а не перебор правок. Тривиальную опечатку или очевидный `null` чини напрямую; для остального фазы ниже пропускай только с явным обоснованием.

Перед стартом прочитай доступные проектные правила и память (`AGENTS.md`, charter, `memory/`): карта слоёв и инварианты сужают пространство причин.

## 1. Построй красный feedback loop

До любых гипотез получи одну команду, которая автоматически ловит именно симптом пользователя и после фикса станет зелёной. Предпочитай:

1. падающий unit/integration/E2E-тест на правильном шве;
2. HTTP/CLI-скрипт с фикстурой и точным assertion;
3. headless-browser сценарий с DOM, console и network assertions;
4. replay сохранённого payload, HAR, лога событий или дампа;
5. одноразовый минимальный harness;
6. автоматическую бисекцию между известными состояниями — только в отдельном worktree или заведомо чистом состоянии, без риска для пользовательских изменений.

Ужимай loop: секунды вместо минут, конкретный симптом вместо «не упало», фиксированные время/seed/сеть вместо флаки. Для недетерминированного бага повышай частоту воспроизведения циклом, параллельной нагрузкой, стрессом и сужением таймингов: 50% воспроизводимости уже можно исследовать, 1% — почти нет.

Если loop не строится, остановись до гипотез. Верни main thread или пользователю: что проверено, какого доступа или артефакта не хватает, какое временное инструментирование требуется.

Критерий фазы: команда уже запущена, краснеет на исходном симптоме, детерминирована, работает без человека и достаточно быстра для повторных прогонов.

## 2. Воспроизведи и минимизируй

Подтверди, что красный сигнал соответствует заявленному багу, а не соседней ошибке. Затем удаляй входы, данные, конфигурацию и шаги по одному, перепроверяя loop после каждого удаления. Оставь минимальный сценарий, где каждый элемент необходим для воспроизведения.

## 3. Сформулируй гипотезы

До проверки первой выпиши 3-5 ранжированных гипотез. Каждая должна предсказывать наблюдаемый результат: «если причина X, то probe Y изменит сигнал так-то». Нефальсифицируемая теория — не гипотеза.

Покажи список main thread или пользователю, но не блокируйся на ответе: при отсутствии реакции проверяй по своему ранжированию.

## 4. Инструментируй по одной переменной

Каждый probe проверяет одно предсказание. Предпочитай debugger/REPL, затем точечные логи на границах, различающих гипотезы. Не логируй всё подряд.

Маркируй временные логи уникальным тегом вида `[DEBUG-a4f2]`, чтобы удалить их одним `rg '\[DEBUG-'`. Для performance-регрессии сначала сними baseline профайлером, timing harness или планом запроса, затем сравнивай; посмертный замер без baseline ничего не доказывает.

## 5. Добавь тест, затем исправь

Перенеси минимальный repro в регрессионный тест на том шве, где баг реально
возникает, но production fix пока не вноси.

До production fix назови изменяемый root seam и инвентаризируй все
обнаружимые repository call sites и соседние пути через него. Используй точные
references, `rg` и принятые project conventions; отдельно пометь dynamic
dispatch, generated code и external consumers как coverage gaps. Не называй
статический список полным, если такие gaps остаются.

Предпочти один scoped root-cause fix одинаковым patches по callers. Inventory
не расширяет согласованный write scope: соседний путь вне scope верни main
thread как evidence/open question. Красный/зелёный сигнал должен доказывать
исходный symptom и применимые соседние пути через root seam, а не только один
call site из репорта. Объём самого исправления проверь по
`$qtim-minimal-diff`.

Если правильного тестового шва нет, не пиши искусственный тест ради галочки.
Зафиксируй архитектурную находку и передай её `qtim-architect` в режиме REVIEW.
Если шов есть: увидь красный тест, внеси minimal root-cause fix, увидь зелёный
тест и перепроверь исходный сценарий из фазы 1.

## 6. Заверши cleanup

- [ ] Исходный loop зелёный.
- [ ] Регрессионный тест в suite или отсутствие шва явно зафиксировано.
- [ ] `rg '\[DEBUG-'` не находит временного инструментирования.
- [ ] Одноразовые harness-файлы удалены, если созданы этим запуском.
- [ ] Подтвердившаяся гипотеза и причина названы в отчёте/коммите.

После фикса спроси, что могло предотвратить класс ошибки. Скрытая связность, отсутствие тестового шва или смешанные обязанности — отдельный вход для архитектурного review, уже на фактах диагностики.
