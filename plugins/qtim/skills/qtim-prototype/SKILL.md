# qtim Prototype

> Дисциплина qtim; Codex-адаптация `prototype` из [mattpocock/skills](https://github.com/mattpocock/skills), MIT.

Разрешай дизайн-развилку конкретным throwaway-прототипом. Сначала сформулируй один вопрос, на который он должен ответить:

- логика или state machine верна — сделай терминальный мини-скрипт с фикстурами и полным состоянием после каждого действия;
- UI должен выглядеть или вести себя определённым образом — сделай несколько радикально разных вариантов на одном dev-роуте, переключаемых через `?variant=a|b|c` и заметный selector.

Три косметических вариации одной идеи не считаются вариантами.

## Правила

1. Сделай throwaway-статус очевидным: `prototype-*` / `proto-*`, узкий новый файл или маршрут рядом с исследуемым модулем. Не меняй существующий production-файл так, чтобы прототип нельзя было отделить.
2. Обеспечь одну команду запуска через штатный runner проекта.
3. Храни состояние в памяти. Если проверяется именно persistence, используй явно временную таблицу/файл с именем `PROTOTYPE-wipe-me` и не затрагивай production data.
4. Не полируй: только запускаемость и fidelity, нужная для ответа. Не добавляй архитектурные абстракции, полноценную обработку ошибок и тестовый suite.
5. Покажи варианты пользователю или decision owner и собери реакцию на конкретное.
6. Запиши вердикт в артефакт, породивший вопрос: design brief, ADR или «Историю изменений» feature-артефакта.
7. Передай выбранное решение в обычный implementation workflow. Production-реализацию начинай только если она входит в исходный или отдельно подтверждённый scope; в противном случае заверши handoff решением и gates. Не эволюционируй прототип в production-код.
8. Удали только однозначно новые throwaway-файлы этого запуска либо оставь их в отдельной throwaway-ветке. Пользовательские существующие файлы без явного разрешения не удаляй.

В main должно жить решение, а не одноразовый эксперимент. Исключение — короткий decision-rich фрагмент (например, state machine или форма типа), который точнее прозы; сохрани только его в design-артефакте.

## Anti-patterns

- Прототип без сформулированного вопроса.
- Один UI-вариант, с которым нечего сравнивать.
- Полировка прототипа вместо получения ответа.
- Переименование прототипа в production без повторной реализации и гейтов.
- Удаление или перезапись пользовательского кода под видом cleanup.
